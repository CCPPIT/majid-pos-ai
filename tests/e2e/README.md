# اختبارات القبول على الجهاز (E2E) — MAJID POS AI

> الحالة: **خطة + سيناريوهات جاهزة** (PHASE 28). لا تُشغَّل تلقائيًا في هذه البيئة
> لأنها تتطلب محاكي/جهاز Android أو iOS وطبقة قيادة أتمتة (Detox/Maestro) غير
> مثبّتة بعد. هذا توثيق صادق وليس اختبارًا مُمرَّرًا بالادعاء.

## لماذا لا تعمل هنا؟
- اختبارات الوحدة والتكامل تعمل عبر Jest في Node (مصادر محاكاة) وتغطي المنطق
  والربط بين المستودعات.
- اختبارات E2E تتطلب: تطبيقًا مبنيًا (`expo prebuild`/توقيع)، محاكيًا أو جهازًا،
  وأداة قيادة (نوصي بـ **Maestro** لبساطته على RN/Expo، أو Detox لتكامل أوثق).
- عند توفّر CI بجهاز/محاكي، تُنقَّل السيناريوهات أدناه إلى تدفقات Maestro/Detox.

## السيناريوهات الحرجة (مسارات يجب أن تُخضَع للاختبار)

1. **بيع → دفع → إيصال**
   - فتح نقطة البيع، إضافة منتج، إتمام الدفع النقدي، ظهور الإيصال، تحدّث الطلبات.
2. **العمل دون اتصال ثم المزامنة**
   - تفعيل وضع الطيران، إجراء بيع (يُحفظ محليًا ويُضاف لطابور المزامنة)، إغلاق
     الطيران، ظهور "مزامنة معلّقة" ثم نجاح الدفع، وتفريغ العدّاد.
3. **القفل التلقائي والفتح**
   - ضبط المهلة "فورًا"، إرسال التطبيق للخلفية ثم العودة → ظهور شاشة القفل؛
     فتح بـ PIN صحيح ينجح وخاطئ يُرفض؛ البصمة تفتح إن فُعّلت.
4. **صلاحيات الدور (إخفاء ليس أمنًا)**
   - تسجيل دخول كاشير: لا يظهر مدخل التقارير/الوكلاء/التدقيق، ومحاولة فتح
     المسار مباشرة محجوبة؛ مدير المتجر يرى التقارير.
5. **Copilot يجيب من بيانات حقيقية**
   - بعد بيع، سؤال "كم الإيراد اليوم؟" يعرض رقمًا يطابق التقرير.
6. **سجل التدقيق يلتقط**
   - بعد بيع ودفع وقفل/فتح، يظهر في شاشة التدقيق مدخلات البيع/الدفع/الأمان
     بمنفّذ وطابع زمني.
7. **حالات الفشل والفراغ**
   - دفعة بنقد غير كافٍ تُرفض برسالة؛ شاشة بلا بيانات تعرض حالة فراغ واضحة.

## استقرار الاختبارات
- بيانات الاختبار تُعزل عبر مسح التخزين في `beforeEach` (نفس نمط تكامل Jest).
- تُستخدم عناصر قابية وصول (`accessibilityLabel`/`accessibilityRole`) الموجودة
  في المكوّنات كمعرّفات (مثل زر الإرسال، إدخال PIN).
